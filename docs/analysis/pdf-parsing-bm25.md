# PDF 첨부 파싱·BM25 색인 개발 설계

- 기준일: 2026-08-31
- 상태: **구현 완료(2026-08-31), 배포 대기.** 파서·DAG·마이그레이션이 워킹 트리에 있다.
  남은 것은 운영 Airflow 이미지 재빌드(PyMuPDF)와 마이그레이션 반영, DAG 켜기다.
  외부 호출도 LLM도 없다
- 입력 계약: [문서 본문·첨부 수집](../collection/document-body-collection.md)
- 상위 설계: [경제 문서 아카이브](economic-document-archive-design.md)
- 보류: [첨부 PDF의 Vision 분석](pdf-vision-analysis.md) — 조건이 관측되면 켠다(12절)

수집한 PDF를 Synology NAS에서 PyMuPDF로 파싱해 첨부 단위 텍스트를 만들고, 문서 단위 BM25로
색인한다. **외부 호출 0, LLM 0, 청킹·임베딩 0이다.**

첨부에만 본문이 있는 문서가 469~772건 있다(한국은행·금감원·BOJ·네이버 리서치). 그 문서들은
지금 제목과 요약만으로 검색된다. 이 설계가 채우는 것이 그 빈칸이다.

**왜 이렇게 작나.** 검색이 BM25 하나이고 우리 첨부는 대부분 디지털 발행 PDF다.
`page.get_text()`가 본문·표 셀·차트 라벨의 글자를 이미 다 주고, 표 구조도
`find_tables().extract()`가 로컬로 만든다. 외부 Vision이 유일하게 더하는 것은 **텍스트
레이어가 아예 없는 페이지의 글자**인데, 그 페이지가 몇 %인지 재 본 적이 없다(2026-08-31
사용자 결정). 재고 나서 켠다.

## 0. 범위

### 포함

- PDF 텍스트 추출과 페이지 단위 처리
- 표 격자를 로컬에서 텍스트로 펴기(`find_tables().extract()`)
- 텍스트가 나오지 않는 페이지를 **기록**하기 (12절 조건의 근거)
- 첨부 단위 텍스트 조립과 저장
- 문서 단위 BM25 색인과 검색 관측
- Synology NAS의 CPU·메모리 제한을 고려한 실행 방식

### 제외

- **외부 Vision 호출** — 보류. 설계는 [pdf-vision-analysis.md](pdf-vision-analysis.md)에 있고
  켜는 조건은 12절
- **청크·임베딩·벡터 검색** — 미룬다. 켜는 조건도 12절
- 페이지 렌더링, 이미지 크롭, 단어 좌표 보존 — Vision이 없으면 소비자가 없다
- HWP·HWPX·XLS·XLSX·DOCX 파싱
- NAS에서 실행하는 OCR·로컬 Vision 모델, Docling
- 하이브리드 순위(RRF)와 재순위
- 검색 API·툴의 응답 계약(부르는 쪽 문서가 갖는다)

## 1. 확정 결정

| 항목 | 결정 |
| --- | --- |
| PDF 파서 | PyMuPDF `==1.28.2` |
| 실행 단위 | 첨부 한 개를 열고 페이지를 순차 처리 |
| 동시 실행 | NAS에서는 파싱 작업 1개 |
| 본문 텍스트 | `page.get_text("text", sort=True)` |
| 표 | `page.find_tables()`의 격자를 `extract()`로 펴서 Markdown 표로 |
| 텍스트 없는 페이지 | 렌더링하지 않고 **기록만** 한다(4.3) |
| 외부 호출 | **없다.** 파싱 태스크에 네트워크 클라이언트도 API 키도 없다 |
| 저장 | 첨부 단위 텍스트를 `document_attachment`에 |
| 검색 | **문서 단위 BM25**(`pg_search` 0.25.2, `pdb.lindera('korean')`). 청킹 안 한다 |
| 임베딩 | **안 한다.** 켜는 조건은 12절 |
| 임계값 | 4.2·4.3의 상수는 잠정값이다. 10절 3단계의 실측으로 확정한다 |

## 2. 전체 흐름

```text
document_attachment(PDF)
        │
        ▼
원본 경로·SHA-256 확인
        │
        ▼
PyMuPDF 페이지 순회
        │
        ├─ 페이지 텍스트
        ├─ 표 격자 → Markdown 표
        └─ 텍스트가 없는 페이지 → 건수만 기록
        │
        ▼
첨부 단위 텍스트 조립 (페이지 표식 유지)
        │
        ▼
document_attachment 에 저장 (상태·SHA·파서 버전)
        │
        ▼
문서 단위 BM25 색인 (pg_search)
  · 청킹 없음, 임베딩 없음
  · document.body 와 첨부 텍스트를 각각 색인하고 조회에서 document_id 로 접는다
        │
        ▼
market-thesis 툴 / apps/api 검색
```

**한 태스크가 파일을 열고 텍스트를 뽑아 저장하는 것으로 끝난다.** 외부를 기다리는 자리가
없으므로 dispatcher도, 요청 상태 머신도, 원장도 없다.

## 3. 입력 계약

처리 대상은 다음 조건을 모두 만족하는 `document_attachment`다.

- `kind='file'`
- `storage_path`가 있고 실제 파일이 존재한다
- 저장 경로의 확장자가 `.pdf`다 — 그 확장자는 `document_body_hourly`가 파일 이름과
  `Content-Type`에서 정해 붙인 것이라 미디어 타입을 다시 볼 필요가 없다(15절 ⑤)
- 아직 처리하지 않았거나(`parsed_sha256`이 NULL), 원본 SHA가 이전 파싱 시점과 달라졌거나,
  파서 판이 올라갔다(`parser_version`이 현재 판과 다르다)

파일이 없으면 파싱하지 않고 상태도 남기지 않는다 — 다음 실행이 다시 집는다.

**디스크의 파일이 행의 SHA와 다른 경우는 저장 시점에 한 번만 본다.** 파서는 읽은 파일의
SHA를 결과에 싣고, UPDATE가 `sha256 = 읽은 SHA`일 때만 걸린다. 파싱 전에 따로 대조하지
않는다 — 같은 조건을 두 번 보는 것이고, 파일이 새것이면서 행도 이미 새 SHA로 갱신돼
있으면 그 자리에서 맞는 텍스트가 저장되는데 사전 대조는 그것을 실패로 세기 때문이다
(15절 ⑤). 0행이면 그 첨부를 실패로 세어 로그에 남기고, 다음 실행이 새 SHA로 다시 집는다.

## 4. 로컬 파싱

### 4.1 페이지 처리

첨부를 한 번 열고 페이지를 순회한다. 다음 첨부로 넘어가기 전에 문서와 페이지 참조를 닫는다.
전체 코퍼스의 페이지 객체를 메모리에 누적하지 않는다.

```python
blocks = page.get_text("blocks", sort=True)
```

- **블록 단위로 읽는다.** 표 셀의 글자를 본문에서 빼고 그 자리에 Markdown 표를 끼우려면
  좌표가 있어야 한다(4.2).
- **단어 좌표(`get_text("words")`)는 뽑지 않는다.** 읽는 쪽이 없다. Vision을 켤 때 bbox가
  필요해지면 그때 다시 넣는다 — 원본 PDF가 보존되므로 다시 뽑는 데 재수집이 필요 없다.
- **페이지를 이미지로 렌더링하지 않는다.** 크롭도 만들지 않는다. 디스크에 새로 쌓이는 파일이
  없다.

#### 읽는 차례는 단을 먼저 본다 (`pymupdf/3`)

`sort=True`도, 그 뒤 y좌표로 다시 정렬하는 것도 **2단 조판에서 틀린다.** 왼쪽 본문 한 줄과
오른쪽 차트 라벨 한 줄이 번갈아 나와 문장이 쪼개진다(⑦에서 관측, ⑧에서 고쳤다).

`reading_order`가 **세로 빈 띠(gutter)를 찾아 단을 가른다.** 빈 띠가 없으면 1단이고 예전과
같은 y축 순서다. 빈 띠를 찾는 조건 셋은 전부 페이지 폭에 대한 비율이라 용지 크기를 안 탄다.

| 조건 | 상수 | 왜 |
| --- | --- | --- |
| 전폭 조각은 빼고 본다 | `FULL_WIDTH_RATIO` 0.60 | 전폭 제목 하나가 빈 띠를 덮으면 2단이 1단으로 보인다 |
| 빈 띠 ≥ 페이지 폭의 2% | `MIN_GUTTER_RATIO` | 그 아래는 낱말 사이 간격이다 |
| 빈 띠 가운데가 폭의 30~70% | `COLUMN_SEARCH_MIN/MAX` | 가장자리의 빈 띠는 여백이다 |
| 양쪽 단에 조각 2개 이상 | `MIN_COLUMN_PIECES` | 오른쪽에 주석 하나뿐인 1단을 2단으로 읽으면 그 주석이 본문 끝으로 밀린다 |

**단을 가로지르는 조각은 띠를 가른다.** 전폭 제목·전폭 표 위아래의 단은 서로 다른 덩어리라,
그것을 무시하면 제목 아래 왼쪽 단이 제목 위 오른쪽 단보다 먼저 나온다.

3단 이상은 다루지 않는다 — 빈 띠를 하나만 찾고, 저장소 코퍼스에 3단 조판이 없다.

#### 머리글·바닥글은 문서 단위로 뗀다 (`pymupdf/3`)

쪽마다 되풀이되는 머리글·바닥글·쪽 번호는 본문이 아니다. BM25에서는 같은 문자열이 문서
전체에 깔려 잡음이 되고, LLM 프롬프트에서는 토큰만 먹는다.

**한 쪽만 보고는 그것이 프레임인지 그 쪽의 제목인지 알 수 없다.** 그래서 판정이 문서 단위다.

1. 위아래 여백 띠(높이의 8%, `MARGIN_BAND_RATIO`)에 든 블록을 후보로 표시한다. **표는 여백에
   걸쳐도 후보가 아니다** — 채택된 표를 프레임으로 오인해 지우면 숫자가 통째로 사라진다.
2. 쪽 번호는 쪽마다 값이 다르므로 숫자를 `#`으로 접는다(`normalize_frame`).
3. `max(2, 쪽 수의 50%)` 이상의 쪽에 나온 줄만 프레임으로 확정한다(`running_frame`).
4. 각 쪽에서 그 줄을 빼고 `visible_chars`도 함께 줄인다(`drop_running_frame`) — 안 그러면
   본문이 없는 스캔 쪽이 머리글 글자 수만으로 `unreadable` 문턱을 넘어 4.3의 집계에서 빠진다.

**문턱을 50%로 높게 잡은 것은 비용이 한쪽으로 기울어서다.** 못 떼면 잡음이 조금 남을 뿐이고,
잘못 떼면 본문이 사라진다. 되풀이가 조건이라 **1쪽짜리 문서는 아무 것도 잃지 않는다.**

### 4.2 표는 격자를 그대로 편다

증권사 리포트와 중앙은행 PDF는 대부분 벡터 PDF다. 표 셀에 텍스트 레이어가 그대로 있고
`find_tables()`가 격자를 이미 알고 있다.

```python
tables = page.find_tables().tables
grid = tables[i].extract()   # 행 × 열 문자열
```

격자를 쓰는 조건은 넷이고, **넷을 다 만족할 때만** 표로 확정한다.

- 채움률(빈 문자열이 아닌 셀 / 전체 셀)이 `MIN_TABLE_FILL` 이상
- 행이 둘 이상, 열이 둘 이상
- 숫자로 읽히는 셀이 하나라도 있음
- **어느 셀도 `MAX_TABLE_CELL_CHARS`를 넘지 않음**

**앞의 셋은 "표인가"를 보고 넷째는 "제대로 잡혔나"를 본다.** `find_tables()`가 열 경계를
실제보다 적게 찾으면 여러 칸이 한 칸에 뭉치는데, 그 격자도 앞의 셋은 통과한다. 채택하면
원본 블록을 버린 자리에 뭉개진 표가 들어가 **페이지 텍스트가 원본보다 나빠진다.**
버리면 구조만 잃고 글자는 남으므로 **비용이 한쪽으로 기울어 있다** — 애매하면 버린다.
넷째 상수만 실측으로 정했다(15절 ⑦).

**확정한 표는 Markdown 표로 편다**(헤더 줄 + 구분선). 단위는 열 이름에 괄호로 붙인다. 그
텍스트가 그대로 BM25 색인과 LLM 프롬프트로 가므로 표기가 갈리면 검색어와 읽는 쪽이 둘 다
흔들린다.

조건을 못 넘긴 격자는 **버리고 페이지 텍스트만 남긴다.** 셀 문자열은 `get_text()` 결과에
이미 들어 있으므로 글자가 사라지지는 않는다 — 잃는 것은 행·열 구조뿐이고, 그 구조가 필요한
경우가 12절의 조건 ②다.

### 4.3 읽히지 않는 페이지는 기록만 한다

텍스트 레이어가 없는 페이지(스캔, 이미지 한 장으로 만든 페이지)는 로컬로 할 수 있는 것이
없다. **렌더링도 외부 호출도 하지 않고 건수만 남긴다.**

```text
visible_chars < 80
and min(sum(image_bbox_area / page_area), 1.0) >= 0.20
    => 읽히지 않는 페이지
```

- 면적은 `page.get_image_info(hashes=False, xrefs=False)`가 준다. 이미지 바이너리는 읽지
  않는다 — 면적 판정에 필요 없다.
- 가장 큰 이미지 하나가 아니라 **합**을 본다. 작은 조각 여럿이 페이지 전체를 이루는 경우가
  있다.
- 첨부마다 그 페이지 수를 저장한다. **이 수가 12절 조건 ①의 유일한 근거다.** 세지 않으면
  "Vision이 필요한가"에 영원히 답할 수 없다.

## 5. 첨부 단위 텍스트 조립

페이지 텍스트를 순서대로 잇고 페이지 표식을 남긴다. 표는 그 페이지의 제자리에 넣는다.

```text
<!-- page:1 -->
로컬 추출 텍스트

| 구분 | 2025 | 2026(E) |
| --- | --- | --- |
| 영업이익(억원) | 1,200 | 1,450 |

<!-- page:2 -->
...
```

- **페이지 표식을 유지한다.** 검색 결과에서 원문 몇 쪽인지 되짚는 유일한 단서다.
- 같은 페이지에서 표는 그 표가 놓인 자리(y축 순서)에 넣는다.
- `document.body`는 건드리지 않는다 — HTML 본문의 원본 의미를 유지하고 PDF 텍스트로
  덮어쓰지 않는다.

## 6. 저장 계약

### 6.1 첨부에 더하는 것

첨부 파싱 결과는 `document_attachment`에 연결한다. 구현 마이그레이션에서 필요한 최소
정보는 다음과 같다.

| 값 | 용도 |
| --- | --- |
| 파싱 상태 | `NULL`은 미처리. 성공·부분 실패·실패·미지원을 가른다 |
| 추출 텍스트 | 5절이 조립한 첨부 단위 본문 |
| 파싱 원본 SHA | 현재 첨부와 결과가 같은 파일에서 나왔는지 확인 |
| 파서 이름·버전 | 규칙이 바뀌었을 때 재처리 대상 판정. 4.2·4.3의 상수가 이 값에 들어간다 |
| 파싱 시각 | timezone-aware UTC |
| 읽히지 않은 페이지 수 | 12절 조건 ①의 근거(4.3) |
| 전체 페이지 수 | 위 값의 분모 |

정확한 컬럼 이름과 CHECK 제약은 파서와 마이그레이션을 같은 작업에서 구현할 때 확정한다.
**읽는 코드 없이 NULL 컬럼만 먼저 추가하지 않는다** — `content_level`이 그렇게 남았다가 운영
태스크를 죽인 적이 있다(본문 수집 문서 5.3).

**매니페스트 파일을 만들지 않는다.** 좌표를 보존하지 않으므로 남길 것이 텍스트뿐이고, 그것은
DB 컬럼 하나다. 파일로 빼면 백업·권한·정리 규칙이 따라온다.

**`document_chunk` 테이블도 만들지 않는다.** 청크는 임베딩이 부르는 비용이고 BM25는 문서
단위로 색인한다(8절).

### 6.2 무엇이 색인을 막나

**막는 것은 파싱 실패뿐이다.** 성공한 첨부는 그 텍스트가 곧 색인 대상이다.

- 페이지 일부가 실패한 첨부는 **부분 실패**로 저장하고, **읽은 페이지의 텍스트는 색인한다.**
  일부라도 찾을 수 있는 편이 아무 것도 못 찾는 것보다 낫고, 나중에 다시 파싱하면 그 행만
  갱신된다.
- 읽히지 않은 페이지가 있는 첨부도 그대로 색인한다. 그 페이지에 글자가 없을 뿐이다.
- **BM25는 행 단위 증분 색인이라 미루는 비용이 싸다.** 임베딩이면 청크 위치가 밀려 문서
  전체를 다시 만들어야 했다. 이것이 BM25를 먼저 놓는 이유 중 하나다.

## 7. 실패 처리

- PDF 열기 실패: 해당 첨부만 실패시키고 다른 첨부 처리는 계속한다.
- 특정 페이지 실패: page와 예외를 기록하고 **부분 실패**로 저장한다. 첨부 전체를 성공으로
  확정하지 않고, 읽은 만큼은 남긴다(6.2).
- 암호가 걸린 PDF: `미지원`으로 확정한다. 다시 시도해도 같은 답이다.
- 원본 SHA 변경: 이전 파싱 결과를 쓰지 않고 다시 처리한다. 파싱하는 동안 바뀌었으면
  UPDATE가 0행이고, 그 첨부는 실패로 세어 로그에 남긴다(3절).
- 첨부 전부 실패: 태스크를 실패시킨다. **재시도가 살아 있는 예외로 올린다**(`OSError`) —
  전부 실패는 마운트·권한처럼 잠시 뒤 풀릴 수 있는 문제라 `retries`가 뜻을 가진다.
  `AirflowFailException`은 재시도를 건너뛰므로 마운트 자체가 없을 때만 쓴다.

**실패한 첨부를 삭제하지 않는다.** 다음 정시 실행이 다시 처리할 수 있도록 상태와 원인을
남긴다. 되돌릴 수 없는 오류(암호, 손상)는 상태로 확정해 큐에서 빼고, 되돌릴 수 있는 것
(파일 없음, I/O)은 상태를 남기지 않아 다음 실행이 다시 집게 한다.

## 8. 검색 — BM25

**임베딩과 벡터 검색을 이 범위에서 뺀다**(사용자 결정 2026-08-31).

### 8.1 왜 BM25가 먼저인가

- **둘 다 인프라 비용이 0이다.** 운영 DB에 `pg_search` 0.25.2가 `shared_preload_libraries`에
  올라가 있고 `pgvector` 0.8.4도 이미 설치돼 있다(2026-08-30 확인). "깔려 있으니 쓰자"는
  어느 쪽의 근거도 되지 않는다. 임베딩 API 비용도 백필 전량이 $1 안팎이라 판단 축이 아니다.
- **갈리는 것은 유지비다.** BM25는 안 쓰면 인덱스 디스크만 먹는다. 임베딩은 안 쓰는 동안에도
  새 문서를 매시간 청킹·임베딩해야 다음에 쓸 때 최신이고, 모델이 바뀌면 전량을 다시 만든다.
- **질의 빈도가 낮다.** 소비자는 market-thesis의 근거 문서 조회와 `apps/api` 둘이고 하루 수십
  회를 넘지 않을 것으로 본다. 이 규모에서 사전 임베딩은 유휴 비용만 만든다.
- **우리 질의는 고유명사가 압도적이다.** 종목명, 정책 용어(`기준금리`·`대차잔고`), 지표명.
  BM25가 잘하는 자리이고, `pdb.lindera('korean')`이 `삼성전자가`와 `삼성전자는`을 가른다.
- 판단 기준으로 [RAG is simpler than you think](https://www.lighthousenewsletter.com/p/rag-is-simpler-than-you-think)의
  단계 구분을 참고했다 — 하루 1,000질의 미만이면 full-text에서 멈추고, 다음 단계는 임베딩이
  아니라 **질의 재작성**이며, "의미 검색 문제"의 상당수가 사실 질의 표현 문제라는 것이다.

### 8.2 문서 단위 색인 (청킹 없음)

**청크를 만들지 않는다.** 청킹은 임베딩이 부르는 비용이고, BM25는 문서 전체를 그대로
색인한다. 청크 크기·겹침을 정하는 일 자체가 없어진다.

색인 대상은 둘이고 **자리가 다르다.**

| 무엇 | 어디 | 왜 나누나 |
| --- | --- | --- |
| 기사 본문 | `document.body` | HTML 본문의 원본 의미를 유지한다 |
| 첨부 텍스트 | `document_attachment`의 추출 텍스트 | `body`에 합치면 원본이 오염된다 |

문법은 버전을 타므로 상위 설계 4절이 실측한 0.25.2 형태를 그대로 쓴다.

```sql
CREATE INDEX document_bm25 ON document
USING bm25 (id, (title::pdb.lindera('korean')), (body::pdb.lindera('korean')))
WITH (key_field='id');
```

- 첨부 텍스트 인덱스도 같은 모양으로 하나 더 만들고, **조회는 둘을 합친 뒤 `document_id`로
  접는다.** 문서 하나에 첨부가 여럿이라(한국은행 4개) 접지 않으면 같은 문서가 여러 번 나온다.
- **조회 축은 기간과 태그가 먼저다.** 상위 설계가 "리포트를 만들 때 문서를 고르는 축은 단어가
  아니라 기간과 태그"라고 정했다. BM25 점수는 그 필터 안에서의 순위다.
- 색인 갱신은 INSERT·UPDATE가 하고 별도 태스크가 없다.

### 8.3 질의 재작성은 지금 만들지 않는다

소비자가 LLM이면 **그 자체가 질의 생성기다.** 재작성 층을 따로 두지 않는다. 사람이 쓰는
화면이 생기고 0건 응답이 실제로 관측되면 그때 만든다 — 질의당 $0.001 수준이고 프롬프트만
고치면 되므로 **재색인이 없다.** 임베딩보다 먼저 시도할 것이 이것이다.

### 8.4 검색을 관측한다

**이 로그가 없으면 12절의 조건에 영원히 답할 수 없다.** 검색 호출마다 남긴다.

- 질의 문자열과 필터(기간·태그·출처)
- 결과 수와 상위 점수
- 부른 쪽(market-thesis 툴 / `apps/api`)
- 0건 여부

색인 뒤에도 원문 PDF와 첨부 SHA까지 역추적할 수 있어야 한다.

## 9. DAG와 NAS 운영

### 9.1 DAG

| DAG | 하는 일 | 스케줄 | 실패 판정 |
| --- | --- | --- | --- |
| `document_attachment_parse_hourly` | 첨부 PDF 파싱과 텍스트 저장 | `20 * * * *` | 항목별 실패 수집. **전부 실패일 때만 죽인다** |

- 분 단위 cron이라 시간대가 값을 바꾸지 않는다. `start_date`는 다른 DAG와 같이
  `pendulum.datetime(..., tz=KST_TIMEZONE)`으로 둔다.
- **다음 시간이 같은 큐를 다시 본다.** 하나가 실패했다고 죽이면 경보만 늘고 고쳐지는 것이
  없다 — `document_ingestion_hourly`와 같은 판정이고 근거는 모듈 docstring의 "실패와 재시도"
  절에 남긴다.
- 큐는 `parsed_sha256 IS DISTINCT FROM sha256 OR parser_version IS DISTINCT FROM <현재 판>`인
  첨부다(3절). **`document_body_hourly` 뒤에 선다** — 첨부 파일이 있어야 파싱할 것이 있다.
- `dag_display_name`은 `📄 첨부 PDF 파싱`이고 `description`·`doc_md`도 채운다(저장소 규칙).
- pool `pdf_parse` 슬롯 1로 NAS에서 하나만 돈다. **pool은 코드로 생기지 않는다** — 없으면
  태스크가 scheduled에 멈춘 채 경고만 남으므로 DAG docstring "필요한 환경"과
  `docs/operations.md`에 적었다. 운영에는 있다(2026-09-01 확인, 15절 ⑤).

### 9.2 NAS 운영 원칙

- 첨부 한 개를 처리한 즉시 결과를 저장하고 메모리를 해제한다.
- 이미지 바이너리를 읽지 않는다. 면적 메타데이터만 본다(4.3).
- **페이지를 렌더링하지 않는다.** 디스크에 새로 쌓이는 파일이 없다.
- OCR·로컬 Vision 모델·Docling은 설치하지 않는다.
- 로컬과 운영 Airflow requirements는 **정확한 PyMuPDF 판을 고정한다**(`==1.28.2`). 두 파일
  (`compose/local/airflow/requirements.txt`·`compose/prod/airflow/requirements.txt`)과
  `pyproject.toml`은 글자 그대로 같은 판을 적고 그 상태를 유지한다. 범위(`>=1.26`)로 두면
  이미지 빌드 시점마다 다른 판이 들어가고, `find_tables()`의 셀 경계 판정이 판마다 달라
  같은 파일에서 다른 텍스트가 나온다(2026-09-01 실측 — 운영 텍스트와 로컬 재파싱이 725건 중
  4건에서 갈렸고, 밀집 표의 셀 하나가 통째로 빠졌다). `read_page`가 표 bbox 안의 블록을
  버리고 Markdown 표로 갈아끼우므로 경계가 한 칸 어긋나면 그 셀 글자가 사라진다.
  하한이 `1.26`이었던 이유는 그 버전에서 `find_tables`의 시그니처가 지금 형태가 됐기
  때문이다(1.25.5와 1.26.0을 실제로 설치해 확인, 2026-08-31).
- **판을 올릴 때는 `PARSER_VERSION`도 함께 올린다.** 텍스트가 달라지는 변경이라 옛 판으로
  만든 첨부가 그대로 남으면 한 색인 안에 두 판의 표가 섞인다.
- **이미지에 pypdf가 이미 있다**(`langchain-neo4j` → `neo4j-graphrag`가 끌고 온다). 그런데도
  PyMuPDF를 넣는 이유는 pypdf에 **표 탐지와 이미지 면적 메타데이터가 없기** 때문이다. 좌표
  없는 텍스트 추출 하나만으로는 4.2·4.3이 성립하지 않는다.
- **PyMuPDF는 AGPL-3.0 또는 Artifex 상용 라이선스 이중 배포다.** 이 저장소는 사내 배치로만
  돌고 외부 공개·상용 재배포를 하지 않으므로(상위 설계 3절 제외 범위) AGPL로 쓴다. 배포
  형태가 바뀌면 이 줄부터 다시 본다.
- **운영 Airflow 이미지 재빌드는 NAS에서만 된다.** 10절 1단계는 사용자가 실행하는 단계이고,
  그 전에는 운영에서 파서가 import되지 않는다.
- 운영 Airflow의 Debian 계열 이미지를 유지하고 Alpine/musl로 바꾸지 않는다.
- 처리 시간, 최대 RSS, 페이지 수, 읽히지 않은 페이지 수를 실행마다 기록한다.
- NAS 컨테이너 이미지 빌드와 단일 PDF smoke check를 통과한 뒤 DAG를 켠다.

## 10. 구현 순서

1. 로컬·운영 Airflow requirements에 같은 PyMuPDF 버전 범위(`>=1.26`)를 추가한다.
   **운영 이미지 재빌드는 NAS 접근이 필요해 사용자가 실행한다.**
2. PDF 한 첨부를 순차 처리하는 파서를 구현한다 — 페이지 텍스트, 표 격자, 읽히지 않는 페이지
   판정(4절).
3. **이미 받아 둔 첨부 PDF로 통계를 뽑는다.** 저장은 하지 않고 수만 센다(10.1).
4. 첨부 텍스트 조립과 저장(5·6절), 마이그레이션·SQL을 구현한다.
5. DAG를 붙이고 NAS 컨테이너에서 CPU·RSS와 파일 권한을 확인한다(9절).
6. 문서·첨부 텍스트에 BM25 인덱스를 만들고 검색 로그를 남긴다(8.2·8.4).
7. 소비자를 붙인다 — market-thesis의 근거 문서 조회, `apps/api`의 검색.
8. Vision과 임베딩은 12절의 조건이 관측된 뒤에 본다. 지금은 만들지 않는다.

### 10.1 3단계에서 무엇을 세는가

이 단계가 4.2·4.3의 잠정 상수를 확정하고, **12절 조건 ①에 답할 수 있게** 한다. 백필 대상
첨부는 이미 NAS에 있으므로 새로 받을 것이 없고, 저장을 하지 않으므로 비용이 0이다.

- 첨부·페이지 총수, 페이지당 `visible_chars` 분포
- **텍스트 레이어가 없는 페이지의 비율** — 이 수가 Vision을 켤지 정한다
- 표 후보의 격자 채움률 분포. 4.2가 로컬로 확정하는 비율이 여기서 나온다
- 첨부 하나의 처리 시간과 최대 RSS, 추출 텍스트의 평균 길이

이 절의 결과는 실측값으로 이 문서에 적는다. 어림값을 적지 않는다.

## 11. 완료 조건

- PDF 텍스트를 원본 첨부 SHA와 함께 첨부 단위로 보존한다.
- 표 격자가 조건을 넘으면 Markdown 표로 펴서 같은 텍스트에 들어간다.
- **파싱 태스크가 네트워크 클라이언트도 API 키도 쓰지 않는다.**
- 읽히지 않은 페이지 수와 전체 페이지 수가 첨부마다 남는다.
- 페이지 일부가 실패해도 읽은 만큼은 저장되고 색인된다.
- 한 첨부의 실패가 다른 첨부 처리를 막지 않는다.
- NAS에서 파싱 작업이 한 개만 실행된다.
- 첨부 텍스트가 문서 단위 BM25로 색인되고, 같은 문서의 첨부 여럿이 한 건으로 접힌다.
- 검색 호출이 질의·필터·결과 수·0건 여부와 함께 남는다.
- 검색 결과에서 원본 document·attachment·page·SHA까지 역추적할 수 있다.

## 12. 나중에 — Vision과 임베딩

둘 다 **설계는 이미 있고 구현만 미룬다.** 조건은 관측으로 판정하며, 문서에 임계를 적어 두고
사람이 기억하는 방식은 쓰지 않는다.

### Vision 분석 — [pdf-vision-analysis.md](pdf-vision-analysis.md)

1. **텍스트 레이어가 없는 페이지가 유의미하게 나온다**(10.1이 센다). 그 문서들은 지금 검색에
   아예 없다.
2. **market-thesis가 첨부를 근거로 읽을 때 표가 깨져 틀린 값을 인용하는 것이 관측된다.**
   4.2의 채움률을 못 넘긴 표가 그 자리다.

### 청크·임베딩 — 상위 설계 6.2

1. 검색이 0건을 내는 비율이 눈에 띄거나, LLM 툴이 같은 뜻을 키워드만 바꿔 재시도하는 패턴이
   보인다 → 먼저 8.3(질의 재작성)을 시도하고, 그래도 남으면 임베딩.
2. "이 기사와 비슷한 것" 류 요구가 실제로 생긴다. BM25로는 안 되는 질의다.
3. 검색 호출이 하루 수백 회를 넘어 순위 품질이 값어치를 낸다.

켤 때도 **전량 사전 임베딩이 아니라 BM25 상위 50~100건을 재순위하는 형태를 먼저 본다** —
그쪽이 싸고, 모델이 바뀌어도 다시 만들 것이 없다.

**둘 다 지금 미루는 비용이 0이다.** 원본 PDF와 텍스트를 보존하므로 켤 때 재수집이 없다.

## 13. 선행 문제

파서가 파일 내용을 정확히 읽어도 그 파일이 원래 문서에 붙었던 파일인지는 증명하지 못한다.
고정되지 않은 첨부 URL이 나중에 다른 파일을 반환할 수 있으므로 수집 시점의 SHA-256, 응답
메타데이터와 문서 ID 관계를 보존해야 한다. 같은 URL의 내용이 바뀌면 새 파일을 과거 문서에
조용히 덮어쓰지 않는다.

**지금 구조에서는 이 일이 거의 일어나지 않는다.** 본문·첨부 큐가 `body_status IS NULL`이라
한 번 성공한 문서는 다시 집히지 않고, 그래서 첨부 파일은 한 번 쓰고 덮어써지지 않는다
(본문 수집 문서 5.1·7.2). 남는 경우는 제공처가 문서를 지워 행을 지울 때인데 첨부는 CASCADE로
함께 사라진다. 그러므로 파서가 할 일은 **매번 SHA를 대조하는 것 하나**이고(3절), 수집 단계에
새로 만들 장치는 지금 없다. 큐 조건이나 재수집 규칙이 바뀌면 이 문단부터 다시 본다.

### 2026-08-31 ④ Vision을 빼고 다시 씀

**사용자 질문 하나가 범위를 절반으로 줄였다** — "Vision으로 파일에서 글자를 뽑는 게 의미가
있는가".

로컬 추출과 겹치는 부분을 따져 보니 이랬다. 본문 글자, 표 셀 글자, 차트 축·범례 라벨은
`page.get_text()`가 이미 준다. 표 구조도 `find_tables().extract()`가 로컬로 만든다.
**Vision이 유일하게 더하는 것은 텍스트 레이어가 없는 페이지의 글자인데, 그 비율을 재 본 적이
없다.** 검색이 BM25 하나이면 차트 산문은 키워드로 잘 걸리지도 않는다.

그래서 1단계에서 뺐다. 함께 사라진 것들:

- 페이지·bbox 렌더링, 크롭 파일, 크롭 보존 규칙 — 디스크에 새로 쌓이는 파일이 0이 됐다
- 요청 매니페스트와 상태 여섯, dispatcher DAG, LangGraph 그래프, 프롬프트 YAML과 판 잠금,
  호출 원장 테이블, 상한 상수 셋, 게이트 상수 여섯
- 단어 좌표 보존(소비자가 없어졌다)과 1쪽 PDF 분리(원래 소비자가 없었다)
- 월 $5 규모의 외부 호출 비용과 그 상한 관리

**남은 것은 파서 하나와 DAG 하나, 마이그레이션 하나, 인덱스 둘이다.** 그리고 10.1이 재는
"텍스트 레이어 없는 페이지 비율"이 Vision을 켤지를 답한다.

### 2026-08-31 ⑤ 구현 검토 — 겹치는 가드와 안 읽는 값

`c0471f1`(파서·DAG·마이그레이션)과 `fc04660`(문서 주소가 파일이면 본문으로 읽지 않는다)을
"불필요한 로직과 논리적으로 이상한 곳"을 기준으로 읽었다. 코드는 동작하지만 같은 일을
두세 겹으로 막는 자리, 주석과 코드가 다른 말을 하는 자리, 만들어 놓고 아무도 안 읽는 값이
있었다. **문서만 먼저 고치고 코드는 승인 뒤에 한다.** 아래 1~8이 고칠 것, 9~11은 기록만이다.

1. **pool `pdf_parse`는 남긴다 — 사용자 결정(2026-09-01).** 검토 시점의 지적은 둘이었다.
   태스크 하나짜리 DAG에 `max_active_runs=1`이면 이미 한 번에 하나만 돌아 pool이 더하는 것이
   없고, pool은 Airflow에 손으로 만들어야 해서 없으면 스케줄러가 `Tasks using non-existent
   pool` 경고만 남기고 태스크가 scheduled에 멈추는데 그 절차가 어디에도 없었다. 운영에 pool이
   이미 있고 동작하고 있어 지우지 않는다. 대신 **빠져 있던 절차를 적었다** — DAG docstring의
   "필요한 환경"과 `docs/operations.md`의 DAG 목록·문서 절. 나중에 NAS CPU를 같이 쓰는 DAG이
   생기면 같은 pool에 물린다.
2. **"재시도할 값어치가 있다"면서 재시도를 막는 예외를 올린다.** 전부 실패 시
   `AirflowFailException`을 올리는데 이 예외는 `retries`를 건너뛴다. `default_args`의
   `retries: 2`가 그 경로에서 죽은 설정이었다. `document_body_hourly`는 같은 자리에서
   `ConnectionError`를 올려 재시도가 산다. → `OSError`로 바꾼다(7절). 마운트 없음 검사의
   `AirflowFailException`은 확정 실패가 맞아 그대로 둔다.
3. **파싱 전 SHA 대조(`FileChangedError`)는 UPDATE의 SHA 가드와 같은 일을 한다.** 파서가
   디스크 SHA와 행 SHA를 대조해 예외를 올리고, `update_parse.sql`의 `AND sha256 = 읽은 SHA`가
   같은 조건을 다시 본다. 사전 대조를 빼면 결과가 더 낫다 — 파일이 새것이고 행도 새 SHA면 그
   자리에서 성공하고(지금은 실패로 센다), 행이 아직 옛 SHA면 0행이라 다음 실행이 집는다.
   본문 수집 문서대로 첨부 파일은 한 번 쓰고 안 바뀌므로 이 길을 실제로 타는 경우는 운영자가
   `body_status`를 NULL로 되돌려 재수집한 때뿐이다. 대신 지금은 UPDATE가 0행이어도 아무 로그
   없이 지나가므로 그 자리를 실패로 세게 한다. → 예외 클래스·사전 대조·DAG의 except 가지·
   테스트 둘이 준다(3절). 대조가 사라지면 `ParseCandidate.sha256`도 읽는 곳이 없어 SELECT와
   함께 뺀다. 큐의 `parsed_sha256 IS DISTINCT FROM sha256` 한 줄은 재큐잉의 유일한 장치라
   남긴다.
4. **`parser_version`은 저장만 하고 큐가 안 본다.** 모델·마이그레이션·파서 주석 셋 다 "규칙이
   바뀌면 올리고 재처리 판정에 쓴다"인데 큐 SQL에 그 조건이 없었다. `pymupdf/2`로 올려도
   아무 첨부도 다시 안 돈다. 14절 3항이 "아직 없다"로 남아 있던 것이 이것이다. → 큐에
   `OR parser_version IS DISTINCT FROM %(parser_version)s` 한 줄을 더하고 14절 3항을
   확정으로 바꿨다. 컬럼이 이미 운영에 있으니 주석을 지우는 쪽보다 쓰는 쪽이 싸다.
5. **DAG의 except 넷이 같은 몸통이다.** `FileNotFoundError`·`FileChangedError`·`OSError`·
   `Exception` 넷이 전부 "경고 로그 + `failures`에 추가 + 다음 첨부"이고 로그 문구만 다르다.
   `document_body_hourly`는 가지마다 행동이 다르지만(unavailable 확정, 문서 삭제) 여기는
   아니다. → `except Exception` 하나에 `logger.exception`. 3번을 적용하면 자연히 셋이 준다.
6. **만들어 놓고 안 읽는 값 셋.** `AttachmentPdfParser.file_root` 프로퍼티(읽는 곳 없음),
   `ParseCandidate.document_id`(SELECT·모델·테스트까지 있는데 파서도 저장도 안 쓴다 — 저장은
   `attachment_id`로 간다), `ParsedPage.tables`(세고 버린다). → 셋 삭제.
7. **`table.extract()`를 표마다 두 번 부른다.** 표 판정(`usable_grid`)에서 한 번, Markdown
   렌더에서 한 번. → 격자를 한 번 뽑아 둘 다 쓴다.
8. **큐 SQL의 군더더기 둘.** `media_type = 'application/pdf'` 절은 본문 수집기의 `_suffix`가
   헤더가 PDF면 이미 `.pdf`를 붙이므로 경로 절이 덮는다 — 남는 경우는 파일 이름이 `.hwp`인데
   헤더가 PDF라는 모순뿐이고 그건 열면 `failed`로 확정될 뿐이다. `parse_status IS NULL OR`는
   NULL이면 `parsed_sha256`도 NULL이고 `sha256 IS NOT NULL`이라 `IS DISTINCT FROM`만으로
   참이다. → 둘 다 뺀다(3절).
9. **(기록만) 문서 주소가 파일이면 같은 파일을 두 번 받는다.** `fc04660`의 갈래가 PDF를 이미
   받았는데 URL만 돌려주고, 첨부 단계가 같은 URL을 다시 받는다. BOJ 한 건당 수 MB × 2.
   지금은 22건 백필과 가끔 오는 새 문서뿐이라 둔다. 잦아지면 `DocumentBody`에 payload를 실어
   넘긴다. **코드에는 아무 표시도 남기지 않는다**(사용자 결정, 2026-09-01) — `collect`가 주소를
   알아내고 `_attach_files`가 받는 것이 이 수집기의 분업이라 그 갈래만 payload를 들고 넘어가는
   쪽이 오히려 예외다. 일부러 낮게 잡은 천장이 아니라 그냥 현재 구조이므로 `ponytail:` 표시가
   맞지 않는다.
10. **(기록만) "y축 순서라 원문 읽는 차례가 유지된다"는 2단 조판에서 틀린다.** 증권사
    리포트의 2단 조판은 두 단이 줄 단위로 섞인다. BM25에는 무관하고 LLM 프롬프트에만 영향이
    있다. 코드는 두고 파서 docstring을 "1단 조판 기준이다"로 사실대로 고친다.
    **⑧에서 고쳤다** — `reading_order`가 단을 가른다.
11. **(사소) 문서와 코드가 다른 말.** 파서 모듈 docstring은 "PDF가 아니면 `unsupported`"인데
    코드는 못 열면 `failed`, 암호만 `unsupported`다. 모델 주석이 맞고 docstring이 틀렸다 —
    docstring만 고친다. `is_html_document`가 `;`로 다시 자르는데 `_header`가 이미 떼서 주는
    것은 무해해서 둔다.

### 2026-09-01 ⑥ 운영 텍스트와 로컬 재파싱 대조

운영 DB의 첨부 982건을 로컬 파일과 대조하고 현재 코드로 전수 재파싱했다. 경로·크기·SHA는
982/982 일치했고 재파싱은 예외 0으로 끝났다. 파싱을 마친 725건 중 **4건이 운영 텍스트와
갈렸다** — 페이지 수와 SHA가 같으므로 파일도 코드도 아니고, 남는 변수는 PyMuPDF 판 하나다.
`>=1.26`은 이미지 빌드 시점마다 다른 판을 넣고 `find_tables()`의 셀 경계가 판마다 다르다.
**`==1.28.2`로 고정했다**(`pyproject.toml`, 로컬·운영 requirements, DAG docstring).

같이 나온 다섯은 설계대로라 손대지 않았다.

- **257건 대기** — `DEFAULT_BATCH_SIZE=50`에 시간당 한 번이고 DAG이 08-31에 섰다. 백필이 도는

- **이미지 PDF가 `ok`인데 `extracted_text`가 NULL** — `assemble`이 일부러 `None`을 낸다.

- **미추출 265쪽(12,310쪽의 2.15%)** — 실패 지표가 아니라 Vision을 켤지 정하려고 모으는 값
  그 자체다(`pdf-vision-analysis.md` 5절). 이 비율로는 아직 켜지 않는다.
- **고아 파일 1건**(`bea/82/0.pdf`, 08-30 20:10) — `_attach_files`가 파일 쓰기와 행 저장을 다른
  트랜잭션으로 두므로 행이 죽으면 파일만 남는다. 큐는 DB 행만 보므로 무해하다.
- 감사 도구가 남긴 유휴 SELECT 백엔드 하나. 코드와 무관하다.

**아직 안 한 것: `PARSER_VERSION` 상향.** 올리면 982건이 전부 큐에 다시 서는데, 그 재처리를

받았는지 먼저 확인해야 한다** — 이전 코드를 돌고 있으면 판을 올려도 한 건도 다시 돌지 않는다.

### 2026-09-01 ⑦ 추출 텍스트를 원문과 대조 — 표 문턱 하나를 실측으로 확정

⑥이 "파서가 자기 자신과 일치하는가"만 쟀다는 것을 확인하고, **추출 텍스트를 원문 쪽과 눈으로
대조**했다(표본 6쪽) 뒤 전수 통계를 냈다(983건·12,323쪽).

**본문은 정확하다.** 1단 조판 본문은 소제목·문단이 원문 순서대로, 오탈자 없이 나온다.

**두 자리가 틀린다.**

- **2단 조판** — 왼쪽 본문과 오른쪽 차트 라벨이 줄 단위로 섞여 문장이 쪼개진다(`상승` / `(%)`
  / `1H25` / `세. 그러나…`). 이미 docstring에 적어 둔 한계이고, BM25에는 무관하나 LLM
  프롬프트에는 영향이 있다. **이번에 고치지 않았다** — ⑧에서 고쳤다.
- **밀집 표** — `find_tables()`가 17열 ETF 표에서 열 경계를 5개만 찾아 헤더와 첫 데이터 행이
  한 셀에 뭉쳤다. 그 격자가 앞의 셋을 통과해 채택되고, `read_page`가 **원본 블록을 버린
  자리에** 그것을 넣어 페이지 텍스트가 원본보다 나빠졌다. **이것을 고쳤다.**

**`MAX_TABLE_CELL_CHARS = 100`.** 채택된 표 2,331개의 "가장 긴 셀" 분포가 p50 39자, p75 84자,
p90 232자다. 뭉개진 사례는 ETF 표 125자, BEA 산업 분류표 2,911자였다. 100자면 3/4의 표가 그대로
남고 두 사례를 다 잡는다. 버리는 비용이 채택하는 비용보다 낮아 문턱을 낮게 잡았다.

효과(전수 재측정): 격자 10,895개 중 채택이 **2,331 → 1,832**(−499). ETF 12쪽은 뭉개진 표가
사라지고 원본 행이 살아났다 — `KraneShares … / Global / 0.69 / 0.2 / (0.1) / 0.6 / 4.9 …`로
행 하나가 열 순서대로 이어진다.

`PARSER_VERSION`을 `pymupdf/2`로 올렸다. 규칙이 바뀌었으므로 첨부 전체가 큐에 다시 선다.

**남은 관측(고치지 않음).**

- 텍스트가 한 자도 안 나온 쪽 96. 그중 48은 `unreadable` 플래그도 안 붙는다(래스터 비율이
  낮아서다). 백지 간지·뒷표지가 여기 섞여 있어 전부가 손실은 아니다.
- 글자 없고 래스터 적은 쪽 205 중 벡터 30개 이상이 50 — 벡터로 그린 도표 의심. 4.3의
  판정이 `get_image_info()`(래스터)만 보므로 265에 안 들어간다.
- 미추출 265의 제공처 쏠림: 국내 증권사 리포트 2.1~4.3%, 한국은행 3.23%, **BOJ·Fed·Census는
  0.00%**. 해외 기관 PDF에는 이 문제가 없다.

**`pymupdf_layout`(1.28.2)이 위 둘을 다 다루는 후보다.** PyMuPDF가 `find_tables()`마다 스스로
권한다. ONNX 모델을 CPU로 돌리는 방식이고 휠이 42.9 MB, 의존성이 `onnxruntime`·`numpy`·
`networkx`·`pyyaml`, 라이선스는 PyMuPDF와 같은 AGPL/상용 이중이다. **도입하지 않았다** —
운영 이미지에 먼저 들어가야 하고, 지금 용도(BM25)에는 필요가 확인되지 않았다.

### 2026-09-01 ⑧ 읽는 차례를 단으로, 머리글·바닥글을 문서 단위로

⑦이 남겨 둔 2단 조판을 고치고, 같이 물어본 "본문이 아닌 것도 다 읽나"에 답했다. **다 읽고
있었다** — `read_page`가 버리던 것은 이미지 블록과 채택된 표 안의 글자 둘뿐이라 머리글·
바닥글·쪽 번호·각주가 그대로 `extracted_text`에 들어갔다.

**셋을 고쳤다.**

- **읽는 차례**(`reading_order`·`column_gutter`) — 세로 빈 띠로 단을 가르고 왼쪽 단을 먼저
  읽는다. 4.1의 표가 조건 넷이다.
- **프레임 제거**(`running_frame`·`drop_running_frame`) — 위아래 여백 띠에서 여러 쪽에
  되풀이되는 줄만 뗀다. 판정이 문서 단위인 이유는 4.1에 있다.
- **가장자리 색인 탭**(`side_strip`) — `1 / 정 / 책`처럼 한 글자씩 세로로 쌓아 가장자리에
  붙인 띠다. 글자가 회전하지 않아 방향으로는 안 잡히고, 본문 쪽에만 있어 프레임 문턱도
  못 넘는다. **이것만 되풀이가 아니라 모양으로 판정한다**(사용자 제보, 2026-09-01).

`PARSER_VERSION`을 `pymupdf/4`로 올렸다. 규칙이 바뀌었으므로 첨부 전체가 큐에 다시 선다.

**실측**(저장소에 받아 둔 첨부 **983건 전수**·12,323쪽. ⑦과 같은 코퍼스다).

**빈 띠를 찾은 쪽의 94.8%에서 차례가 실제로 바뀐다**(무작위 200건 표본, 403/425). 나머지
5%는 조각이 전부 한 단에 몰려 있어 가르나 마나 같은 쪽이다 — 이 규칙이 헛돌지 않는다는
증거이자, **오검출이 곧 오정렬은 아니라는 뜻**이기도 하다.

**제공처별 2단 판정**(각 12건·최대 10쪽): 증권사 리포트 21.3%, BOJ 9.0%, 한국은행 5.3%,
백악관 2.4%, BEA 1.6%, Fed·Census 0.0%. **1단이 확실한 제공처에서 낮게 나오는 것이 이
규칙이 오검출을 안 만든다는 증거다.** 그쪽에서 빈 띠를 찾은 몇 쪽도 조각이 전부 한 단에
몰려 있어 차례가 바뀌지 않았다(한국은행 `83438/3.pdf` p3 확인).

**뺀 것의 얼굴**(정규화한 모양): 쪽 번호가 `#`·`- # -`·`# / #`로 대부분이고, 리포트의 머리글

`TUESDAY, December #, #`가 나온다.

**문턱을 50%로 잡아 일부러 덜 뗀다.** 40쪽짜리 리포트의 머리글이 9쪽에만 있으면 안 뗀다 —
못 떼면 잡음이 조금 남을 뿐이고 잘못 떼면 본문이 사라진다. 그래서 뺀 글자가 1%뿐이다.

**색인 탭은 저장소 코퍼스에 없다.** 제보 문서(`SPRi_AI_Brief_8월호.pdf`, 29쪽 중 13쪽)로

있고 손해가 없다.** 그래도 지금 코퍼스만 보면 YAGNI이므로, 새 출처가 안 늘면 빼도 된다.
