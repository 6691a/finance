# LLM 브리핑 확장 로드맵

- 날짜: 2026-08-19
- 상태: 제안 (미구현)

## 0. 목적과 범위

[Slack 정기 리포트 설계](slack-report-design.md)의 브리핑들이 자리를 잡은 뒤, 수집 중인
데이터 가운데 **LLM의 판단이 필요한** 세 가지 확장을 정리한다. 표로 그릴 수 있는 것은
이미 브리핑에 들어갔다(증시자금·공매도·실시간 환율·크립토·금리 스프레드, 2026-08-19).
여기 남긴 것들은 점수나 규칙으로 답이 나오지 않아 모델이 골라야 하는 일이다.

세 기능 모두 기존 인프라를 재사용한다. 새 수집 DAG는 없다.

- 모델 정의는 `airflow/modules/llm.py`가 코드로 정한다. 제공처를 환경변수로 갈아 끼우지 않는다.
- 흐름 제어는 LangGraph, 데이터 모양은 Pydantic, 재시도는 Airflow(클라이언트 `max_retries=0`).
- **숫자는 전부 SQL이 만들고 LLM은 숫자를 만들지 않는다.**
- LLM이 실패해도 리포트는 나간다. 실패했다는 사실을 메시지에 남긴다.
- 블록에 없는 내용을 LLM 입력에 주지 않는다. 화면에 없는 숫자를 모델이 쓰면 안 된다.

권장 구현 순서는 **2절(시장-뉴스 연결) → 1절(공시 선별) → 3절(주간 종합)** 이다.
2절이 가장 싸고(반나절 규모, 신규 DAG 없음) 급락일에 바로 값어치가 보인다.
1절은 공시 데이터가 2026-08-16부터라 조금 더 쌓인 뒤 검증하기 좋고,
3절은 주간 집계가 의미를 가지려면 몇 주치가 필요하다.

## 1. 공시 선별 브리핑

### 데이터

`dart_disclosure_intraday`가 채우는 `disclosure_event`와 `earnings_fact`.
현재 어느 리포트도 읽지 않는다.

### 왜 LLM인가

상장폐지·유상증자·자사주 취득·최대주주 변경 같은 공시의 중요도는 점수 컬럼이 없고,
목록 전체를 놓고 상대 비교해야 갈린다. 문서 브리핑에서 상위 동점 구간의 순서를
모델에 맡긴 것과 같은 상황이다.

### 방식

문서 브리핑의 `modules/briefing/picks.py` 패턴을 그대로 쓴다.

- 하루치 공시 목록(제목·유형·종목·시각)을 **한 번에** 모델에 주고 "주목할 공시 + 이유
  한 줄"을 고르게 한다. 건별 호출로 쪼개지 않는다.
- 실적 숫자(YoY·QoQ)는 SQL이 계산해 표로 그리고, "서프라이즈인가"의 해석만 모델이 쓴다.
- 선별이 실패하면 시간 역순 전체 목록으로 폴백하고 리포트는 그대로 나간다.
- 0건이면 모델을 부르지 않는다. 고를 것이 없는데 고르라고 시키면 없는 이야기를 지어낸다.
  다만 0건이어도 메시지는 보낸다(문서 브리핑과 같은 생존 신호 원칙).
- 허용 식별자는 목록으로 강제한다. 모델이 목록 밖 공시 ID를 돌려주면 그 항목만 버린다
  (`DocumentPicker.allowed_ids`와 같다).

### 배포 형태

별도 DAG `slack_disclosure_briefing`을 권장한다. 공시는 장중 속보성이 있어
하루 1회 아침에 도는 문서 브리핑과 주기가 다르다. 채널은 문서 채널을 같이 쓰거나
`SLACK_CHANNEL_DISCLOSURE`를 새로 둔다.

## 2. 시장-뉴스 연결 (한국장 요약 강화)

### 문제

한국장 브리핑의 요약 LLM(`BriefingCommentator`)은 시세·수급·증시자금만 본다.
"코스피 -5.5%"는 알지만 **왜**인지 모르므로 "급락했다" 이상을 쓸 수 없다.
같은 시각 문서 파이프라인에는 "매도 사이드카 발동", "미 30년물 5.33% 신고점" 기사가
`value_score` 8점으로 평가되어 있다 — 두 파이프라인이 서로를 모른다.

### 방식

- `market.comment_input`에 당일 `value_score` 상위 문서 중 추적 종목
  태그(`document_instrument`의 005930·000660)가 붙은 것의 **제목과 요약**을 추가한다.
  모델이 시세와 기사를 한 입력에서 보고 원인을 연결해 쓴다.
- **블록에도 "관련 뉴스" 링크 2~3개를 함께 싣는다.** 요약이 언급하는 근거가 화면에
  없으면 안 된다. 하나은행 고시를 뺄 때 입력에서도 함께 뺀 것과 같은 원칙의 반대 방향
  적용이다.
- 조회는 `collect_summary`에 SQL 하나 추가로 끝난다. 신규 DAG·신규 모듈 없음.
- 문서가 0건인 날은 섹션과 입력 모두 조용히 생략한다. 정상 흐름이다.

### 경계

기사 본문은 주지 않는다. 제목+평가 요약이면 원인 연결에 충분하고, 본문을 실으면
프롬프트가 커지고 LangSmith 추적으로 나가는 원문 범위도 넓어진다.

## 3. 주간 종합 리포트

### 방식

주말 아침 1회 도는 새 DAG. 새 수집 없이 조합만 한다.

- 한 주 시세·수급 추세: `modules/briefing/trend.py`의 `summarize`를 주간 구간으로 재사용.
- 금리·스프레드의 주간 변화, 증시자금 주간 증감: 기존 테이블에 주간 집계 SQL 몇 개.
- 그 주 문서 하이라이트: `value_score` 상위 + 문서 브리핑이 이미 고른 것들.
- LLM은 이 집계 전부를 한 입력으로 받아 **서술형 주간 요약**을 쓴다. 숫자는 표가 들고
  있고 모델은 흐름과 연결만 쓴다.

### 시기

공시·실적 수집이 2026-08-16 시작이라 지금 만들면 첫 리포트가 빈약하다.
몇 주치가 쌓인 뒤에 만든다. 그때 1·2절이 이미 있으면 주간 리포트는 그 산출물을
재인용하는 형태가 되어 더 싸진다.

## 4. 만들지 않는 것

- **체크포인터·persistence** — 재실행 단위는 Airflow 태스크다.
- **리포트 저장 테이블** — Slack 메시지가 산출물의 전부다. 재현 가능한 저장용 리포트는
  [경제 문서 아카이브 설계](economic-document-archive-design.md) 4단계의 몫이고,
  여기 기능들이 그쪽으로 자라기 시작하면 그건 4단계 구현이다.
- **건별 LLM 호출** — 선별·요약은 항상 목록 전체를 한 번에 준다. 건별로 쪼개면 상대
  비교가 불가능해지고 호출 수만 는다.
